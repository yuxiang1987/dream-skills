# 页面契约

本契约有两种用法，别混：

- **脚本路径（全新批次）**：`scripts/batch.py build` 按下面的固定模板生成四类页面并校验必填字段。
- **默认研究与增量路径（单篇或已有知识库）**：按同一结构写，但允许按题材调整小节；已有 source 增量补充，不整篇覆盖；单篇不建 comparison。

媒体边界随实际材料走：看过就写看过哪些，没看就写未看，不强制写"图片、动图和视频未核看"。

## 一、source 拆解页（`wiki/sources/`）

frontmatter：

```yaml
---
title: <短标题，全库唯一>
type: source
tags: [公众号, 对标拆解, <作者>]
status: 稳定
sources: ["raw/article/<作者>/<原文文件>.md"]
created: 2026-10-23
updated: 2026-10-23
---
```

正文固定小节顺序：主问题与证据身份 → 标题与开头 → 结构推进 → 案例、解释与观察 → 原文定位锚点 → 结尾怎样收束 → 失败、限制与不宜照搬处 → 可迁移写法与自己的待测方向 → 相关页面。

必含要点：实际阅读范围（文字／图片／视频各看到什么）、哪些数据属作者报告或官方主张未独立核实、来源路径、原文署名时间、原文直链（没有就写未记录）、待测方向。媒体全未看时如实写"图片、动图和视频未核看"。

## 二、作者写法页（`wiki/topics/<作者>文章写法拆解.md`）

frontmatter 的 `sources` 由脚本按本批原文自动填写，正文由人工写，建议结构：

1. 说明依据本批几篇、媒体未核看、结论只在本批范围内成立。
2. 逐篇入口表：编号、拆解页、主类型、主问题。
3. 这批样本怎样写：按标题开头、案例推进、解释方式、结尾归拢四段归纳。
4. 值得迁移的编辑动作：写成可执行动作。
5. 证据与迁移边界：这批必须保留的区分。
6. 与已有对标的关系：和知识库里其他作者的差异，能比就比，不能比就说明。

每篇拆解页都要被作者页链接，脚本会检查。

## 三、对比页（`wiki/comparisons/`）

frontmatter：`type: comparison`，`sources` 写本批全部原文。

正文建议：一张对照表（作者、样本、主要承诺、结构主轴、证据身份）→ 分歧点 → 冲突记录 → 可直接借鉴的共同动作 → 各自不适用的地方。

冲突写法：两方都写清各自出处、时间和适用条件，标 `status: 有冲突` 或在正文标「有冲突」，不替作者裁决，也不删掉其中一方。

## 四、维度库增量（`dimensions.json`）

格式：

```json
[
  {
    "file": "文章标题库",
    "body": "## <小节标题>\n\n<正文，Obsidian 双链引用本批页面>"
  }
]
```

`file` 必须是已存在的维度页（`wiki/topics/` 下）。`body` 的第一行会作为去重标记，重复追加会被脚本拒绝。

常用维度页：文章标题库、文章写法库、观点与表达库、选题问题库、AI写作案例库、证据与边界库。

## 索引与日志

- `wiki/index.md`：脚本更新「最近更新」「知识页：N 页」「原始资料：N 篇」，并在「## 概念」之前插入本批小节，列出作者页与每篇拆解页。
- `wiki/log.md`：脚本追加 `## [YYYY-MM-DD] benchmark-analysis | <批次标题>` 条目，写清作者、篇数、产出页数与未核看范围。

## 五、案例卡（`wiki/topics/AI写作案例库.md` 增量）

带实测案例的文章，除 source 页外补一张案例卡，记**测试设计**而不是复述过程：

```markdown
### 案例：<一句话任务名>（<账号>，<日期>）

- 测什么模型／产品：
- 测试角度：这篇在观察哪项能力，用一个可判定的问题表述
- 步骤：怎么做的，按动作顺序写；只写原文给过的步骤
- 输入：素材、约束、提示词要点（可读到的原文片段）
- 验收点：凭什么算通过或不通过
- 结果与边界：作者报告了什么，缺什么证据
- 出处：来源页 + raw 路径
- 我们能不能复用：需要什么素材与权限，标待实操
```

合并进案例库时按现有分类插入，不新建平行库；同一案例不重复登记。作者没有给出的字段写"未提供"，不替他补。案例是**设计参考**，不是我们的实测结果。
