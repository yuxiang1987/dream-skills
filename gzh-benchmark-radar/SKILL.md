# 公众号对标雷达

把「对标更新了没有、哪篇算真的高、同题有没有重复」变成可复核的数据，再把线索交给选题技能。**只做采集、统计与聚合**：选题取舍、实测、正文、发布都不在这里做。

## 何时用

- 「今天对标的号有没有更新」「把这批没入库的采下来」
- 「算一下各号的阅读基线，哪篇是真爆」
- 「Kimi 3.1 Pro 是不是好几个号都写了」
- 定时任务每天的入口

## 四条硬规则

1. **只新增不覆盖。** 原文按链接去重，同链接已存在就跳过；内容变了才另存快照。不改删任何已有 `raw/` 文件。
2. **付费接口按次计费。** `fetch` 与 `stats` 会扣费，只有用户说「跑一次」或定时任务到点时才执行；`plan` 与 `report` 是纯本地读，不花钱。跑完如实报成功与失败数。
3. **凭据不落地。** 只从 `TIKHUB_API_KEY` 或知识库 `.local/tikhub.json` 读，不写进任何文件、不进日志。
4. **采集不等于入库。** 原文落盘后仍是「未入库」，要有 source 页引用才算拆过；`report` 会列出未入库清单。

## 流程

```powershell
# 1 先看本地状态，不发请求
python scripts/ingest.py --root "<知识库根>" plan --accounts "<账号清单.json>"

# 2 采集：白名单账号最近 N 篇，只新增
python scripts/ingest.py --root "<知识库根>" fetch --accounts "<账号清单.json>" --limit 30 --date <YYYY-MM-DD>

# 3 取互动数据并算各号中位数基线（按次计费）
python scripts/ingest.py --root "<知识库根>" stats --batch "<批次目录>" --date <YYYY-MM-DD>

# 4 汇总异常样本、跨账号事件簇、未入库清单
python scripts/ingest.py --root "<知识库根>" report --batch "<批次目录>"
```

命令须从本技能目录运行，或把 `scripts/ingest.py` 换成实际绝对路径。账号清单格式见 [references/accounts.example.json](references/accounts.example.json)：`name` 是对外名称，`username` 是 `gh_` 原始 ID，`directory` 可指定已有 raw 子目录。

## 去重三层（不要混）

| 层 | 键 | 谁做 | 冲突时 |
| --- | --- | --- | --- |
| 原文 | `app_msg_id:idx`，没有则规范化链接 | 脚本自动 | 同 ID 只留一条 |
| 作品 | 原链接＋作者＋原题＋正文比对 | 人工判断 | 同一篇再发（正文几乎一致）共用一个 source 页，但保留两个链接与原文 |
| 选题 | 主对象＋时间窗聚成事件簇 | `report` 给出候选，人工确认 | 同一事件只出一条候选，账号差异作为切入角度备选 |

只看标题会出错：标题相近可能是不同作品，正文一致可能是同一篇再发。

## 数据口径（写进报告，不许简化掉）

- **单次快照**：阅读数会继续涨，跨日比较无意义。
- **含系统推荐**：不是自然阅读；同一号不同发布时间的推荐量也不同。
- **10 万封顶**：超过的显示为 100001。
- **跨号不可比**：中位数只在该号内部成立，绝对阅读数不同号没有可比性。
- **基线用中位数**：避免个别爆款拉高。异常判定默认 ≥2× 中位数，阈值可调。
- 阅读高只说明这篇在**它自己的号**里突出，不说明某个标题或结构导致传播，也不说明我们照写能到同样量级。

## 输出：候选选题

每条候选独立成块，固定六行，不用表格：

```
### 候选1：「对标文章原标题，原文照抄」（原文链接）
切入角度：<从哪进这个题，八类入口的一句话>
对标名称：<账号名>
类型：<实践型／解决问题型／整活型／教程型／观点型／资讯型>
热点：<热点 或 长青>
日期：<原文发布时间>
```

- 候选行必须是**对标原文标题**，方便作者一眼对上原文；自己要怎么写放切入角度与推荐题里。
- 类型六类的口径、文章结构怎么选、时效四类怎么处理，见 [references/selection-rules.md](references/selection-rules.md)。
- 同一事件簇只出一条候选；已在事件簇里的其他账号作为备选角度附在后面，不重复出题。
- 至多 3 条，推荐 1 条；候选不足不凑数。

## 与其它技能分工

- 候选取舍与最小实测设计交 `gzh-topic-planning`；本技能只提供材料与数据。
- 逐篇拆解入库交 `gzh-benchmark-deconstruct`（若已安装），未安装时只报未入库清单，不自称已拆。
- 正文、标题、封面、排版、发布都由各自技能与作者完成；本技能不写正文、不代实测、不发布。

## 定时任务

`plan` 可随时跑；`fetch` 建议每天一次、每号 30 篇；`stats` 与 `report` 跟着同一次批跑。定时任务只做到「采集＋基线＋事件簇＋未入库清单」，**选题与实测仍要作者参与**，不因为自动化就把亲测这关交出去。

## 验收

- [ ] 采到的每篇都能在 `raw/` 找到，且没有改动任何已有原文
- [ ] 批次清单记录了账号、链接、发布时间、原文指纹、成功与失败数
- [ ] 基线表有账号、有效篇数、中位数、最低、最高
- [ ] 异常样本列出倍数与分享、评论数，并写明口径限制
- [ ] 事件簇列出覆盖账号数与时间跨度，同题没有重复出候选
- [ ] 未入库清单与实际 `wiki/sources` 引用一致
- [ ] 报告没有把高阅读写成爆款因果，也没有声称已实测

维护时用 [tests/cases.md](tests/cases.md) 核对判断口径，脚本行为见 [tests/test_ingest.py](tests/test_ingest.py)。
