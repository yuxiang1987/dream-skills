# 公众号日更流水线（总调度）

一句话：**每个环节只干一件事，交接靠文件契约，验收靠脚本，出错能续跑。**

本 Skill 不重复实现各环节的能力，只负责三件事：决定现在该跑哪一步、把上一步的产物接给下一步、在每道关口检查交付物是否合格。真正的策划、写作、排版由各自 Skill 完成。

## 何时用

- 「跑今日流水线」「开始今天的公众号」「选题到排版一条龙」
- 「把这几个公众号 Skill 串起来」「按流程走一遍」
- 「上次断在写稿了，继续」
- 单环节需求不要用本 Skill，直接调用对应 Skill。

## 流水线全景

七个阶段，四个人工关口。S3 是硬关口：没有作者实测记录，正文不能确认完成。

| 阶段 | 做什么 | 调用 Skill | 交接产物 | 关口 |
| --- | --- | --- | --- | --- |
| S0 定盘 | 读账号宪法与知识库，确认赛道、受众、备胎选题 | 只读 | `00_style.md` | 自动 |
| S1 选题 | 从可核实线索比较至多3个候选，推荐1个小试任务 | `gzh-topic-planning` | `01_选题卡.md` | 人工同意进入实测 |
| S2 案例与实测 | 案例决策卡 + 准备素材与提示词 | `wechat-article-writing` | `02_案例决策卡.md`、`03_证据与实测.md` | **硬关口**：作者亲测 |
| S3 写作 | 按结构写正文 | `wechat-article-writing` | `04_正文.md` | 人工审稿 |
| S4 定稿检查 | 四层 AI 味、病句、事实边界、阅读承诺 | `gzh-final-check` | `05_检查报告.md` | 人工确认：必须修改项清零 |
| S5 标题封面排版 | 拟标题、生成封面、渲染富文本 | `wechat-article-writing`、`gzh-webchat-cover`、`md-wechat-layout` | `06_标题.md`、`07_封面.png`、`08_排版/` | 人工选定标题 |
| S6 发布与回流 | 人工粘贴发布，成稿回流入库 | 人工 + 知识库入库 | `09_发布记录.md` + wiki 页 | 人工发布与入库 |

阶段产物、字段和状态取值见 [references/handoff-contract.md](references/handoff-contract.md)；每阶段的自查清单见 [references/stage-checklists.md](references/stage-checklists.md)。

## 运行目录

一次生产一个目录，目录名 `YYYY-MM-DD-选题短名`：

```text
<工作根目录>/2026-10-23-豆包双11商品图/
├── 00_style.md          账号宪法（流水线唯一基准）
├── 01_选题卡.md          S1 产出
├── 02_案例决策卡.md      S2 产出
├── 03_证据与实测.md      S2 产出 + 作者实测记录
├── 04_正文.md            S3 产出
├── 05_检查报告.md        S4 产出
├── 06_标题.md            S5 产出
├── 07_封面.png           S5 产出
├── 08_排版/              S5 产出（.preview.html / .wechat.html / .report.json）
└── 09_发布记录.md        S6 产出
```

工作根目录默认取 `E:\work\wechat-assistant\pipeline`，可用 `--root` 覆盖。仓库内的 `output/` 与 `wechat-output/` 只放渲染中间产物，不作为流水线工作目录。

## 开始之前

1. 确认 `00_style.md` 存在。首次使用先按 [templates/00_style.md](templates/00_style.md) 补全，内容来自知识库的 `[[concepts/公众号写作风格DNA]]`、`[[entities/程序员拾梦]]` 和往期文章索引，不要凭印象写。
2. 运行脚手架，生成当次目录和全部模板文件。
3. 读 `wiki/index.md` 找到本次能用得上的知识页，再决定从哪一步开始。已有实测材料和成稿时，从对应阶段接上，不必从头跑。

```powershell
python scripts/pipeline.py init --root "E:\work\wechat-assistant\pipeline" --date 2026-10-23 --slug "豆包双11商品图"
```

`--slug` 省略时用 `选题` 兜底；同名目录已存在时不覆盖，直接提示。

## 逐阶段执行

### S0 定盘

读 `00_style.md`，对照本次选题是否落在聚焦领域内、是否符合受众定位。落不进去就换题，不要靠写作硬掰。选题当天没有热点可用备胎池时，说明用了哪条备胎。

### S1 选题

调用 `gzh-topic-planning`，先读账号定位、已发内容与历史反馈，再按适用来源搜集线索：异常表现文章、商业合作样本、官方产品变化、真实实操、读者问题、旧文延伸与时间节点。

- 至多3个候选，写明来源与未知项、目标读者、具体任务、相对旧文新增价值及执行条件；不足不凑数。
- 不设统一分数门槛；比较读者价值、时间价值、可展示性、成本与商业适配，明确推荐1个及其余暂缓理由。
- 将推荐题、最小试跑、退出条件写进 `01_选题卡.md`；作者同意进入实测后才改成 `已确认`，不表示预期结论已证实。

确认是人工关口。S2首轮试验若发现关键前提不成立，回到S1并退为待确认，缩小任务或换备选，保留变更理由；实测结果出来后再收敛正式文章承诺，不为锁题硬写。

### S2 案例与实测

调用 `wechat-article-writing` 做案例策划，产出 `02_案例决策卡.md`：读者问题、候选案例及来源、自己有没有真实素材、最小可执行版本、验收方法、预计耗时与成本、可展示产物、尚未满足的条件。

再准备 `03_证据与实测.md` 的记录位，交给作者实操。**助手不代填结果**，不把预期写成结论。作者实操后把首次结果、失败、提示词或操作修改、再次结果、人工接手、耗时与费用分别记进去。

这一阶段没记录，流水线到 S3 就会停。

### S3 写作

调用 `wechat-article-writing` 写 `04_正文.md`。材料足够就直接写完整正文，不强制多版。材料不足时只交付带 `【待补：…】` 标记的骨架，并在交付说明里列出缺口。

正文里出现的提示词、截图、视频和耗时必须来自 `03_证据与实测.md` 的记录。

### S4 定稿检查

调用 `gzh-final-check` 检查 `04_正文.md`，产出 `05_检查报告.md`。默认只检查不改文件；作者要求修改时再定向改，并重新检查。

「必须修改」还有条目时流水线不能往下走。作者确认后把报告状态改成 `已确认`。

### S5 标题、封面、排版

1. 用 `wechat-article-writing` 基于正文与实测拟标题，写进 `06_标题.md`；默认提供少量不同角度，不强制凑公式或统一字数。作者选定一条后标 `已选定`，标题不超出真实证据。
2. 用 `gzh-webchat-cover` 按选定标题生成 `07_封面.png`（900×383）。封面承诺不能超过正文证据。
3. 用 `md-wechat-layout` 渲染 `04_正文.md`，输出到 `08_排版/`，默认主题「晴蓝手记」。排版只翻译格式，不改字。

### S6 发布与回流

作者把 `08_排版/.wechat.html` 的富文本粘进公众号草稿，人工预览后发布，发布结果记进 `09_发布记录.md`（平台、发布时间、阅读、留言、异常）。

回流入库是本流水线相对通用模板的关键增益：把成稿写成知识库 source 页，更新受影响的 concept、entity、topic 页，运行 `python scripts/wiki_lint.py`，最后在 `wiki/log.md` 记一笔。

## 交接与验收

每个阶段文件都有固定 frontmatter，是机器可读的交接凭证：

```yaml
---
stage: S1 选题
status: 已确认
topic: 一句话主问题
source_skill: gzh-topic-planning
created: 2026-10-23
updated: 2026-10-23
---
```

`status` 只取 `待办`、`待确认`、`已确认`、`已跳过`、`已废弃` 五种。阶段必须按顺序推进：前一阶段是 `已确认` 或 `已跳过`，后一阶段才能是 `已确认`。

校验和续跑：

```powershell
python scripts/pipeline.py check --dir "<当次目录>"
python scripts/pipeline.py status --dir "<当次目录>"
```

`check` 会报出：缺文件、frontmatter 字段缺失、状态取值非法、顺序倒置、已确认阶段还留着 `{{占位符}}`、正文已确认但实测记录为空、检查报告已确认但仍有必须修改项。`status` 打印一张阶段状态表，用来判断从哪一步接上。

能用脚本判定的交给脚本，判断留给人和模型。

## 降级与断点续跑

- **选题不过线**：总分不够就换候选；当天没有可用热点，启用 `00_style.md` 的常青备胎并在 `01_选题卡.md` 标注「常青备胎」，不空转。
- **没条件实测**：S2 标记 `已跳过`，S3 只写骨架，交付说明列出缺什么，不把策划预期写成实测结论。
- **单个 Skill 不可用**：按用户要求直接完成该环节的产物，不假称已调用其他 Skill。
- **中途失败**：修好后重跑该阶段，`check` 给出第一个未通过的关口，失败不重来。
- **排版有警告**：保留 `04_正文.md` 与 `.report.json`，报告警告，不把本地预览通过说成微信验收通过。

## 不做的事

- 不替作者实测，不编造结果、经历、感受、耗时、费用或效果。
- 不自动发布、不自动投稿、不自动联系品牌。
- 不把对标文章的数字、结论或案例当成作者亲测证据。
- 不在每一篇强制多版、强制固定字数或强制凑案例数。
- 不代替各环节 Skill 的专业判断；本 Skill 只管顺序、交接和验收。

## 自检清单

交付前逐条确认：

- [ ] `00_style.md` 已存在且本次选题在聚焦领域内
- [ ] `01_选题卡.md` 有至多3个有依据候选、取舍理由、最小试跑与作者确认记录，不以评分代替判断
- [ ] `02_案例决策卡.md` 写明读者问题、素材、验收方法和未满足条件
- [ ] `03_证据与实测.md` 有作者实测记录；没有记录时正文只到骨架
- [ ] `04_正文.md` 的提示词、截图、视频、耗时都能追溯到实测记录
- [ ] `05_检查报告.md` 的必须修改项已清零
- [ ] `06_标题.md` 已选定一条，标题与实测证据一致
- [ ] `07_封面.png` 是 900×383，承诺不超过正文证据
- [ ] `08_排版/` 有 `.preview.html`、`.wechat.html`、`.report.json`
- [ ] `09_发布记录.md` 记了发布结果，或明确标为待发布
- [ ] 成稿已回流入库并跑过 `wiki_lint.py`，`wiki/log.md` 已记
- [ ] `python scripts/pipeline.py check --dir "<当次目录>"` 通过

维护本技能时用 [tests/pipeline-cases.md](tests/pipeline-cases.md) 逐项模拟回归，脚本检查见 `scripts/pipeline.py` 与 `tests/test_pipeline.py`。
